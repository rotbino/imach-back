# iMach — B2B Wholesale Marketplace & Matching Engine

> **"ای‌مچ"** = "match" به فارسی — پلتفرم تطابق و اتصال خریداران و فروشندگان عمده.

## چیست iMach؟

iMach یک **شبکه اجتماعیِ عمده‌فروشی** است که خریداران و فروشندگان را بر اساس کالا، حجم، قیمت و جغرافیا به هم وصل می‌کند. مثل اینستاگرامِ تجارت عمده — کاربران محلی هستند، ولی زیرساخت جهانی.

### هدف اصلی

**پیشنهاد بهترین و به‌صرفه‌ترین تامین‌کننده به خریدار، و بالعکس، معرفی خریداران با حجم مناسب به تامین‌کنندگان.**

موتور تطابق (`matching engine`) عوامل زیر را در نظر می‌گیرد:
- کالا (Good + Product)
- برند
- ویژگی‌ها (attrs: وزن، بسته‌بندی، نوع، ...)
- قیمت
- موجودی / حجم خرید
- جغرافیا (شهر، استان، کشور)
- حداقل سفارش

در آینده، برای خریدهای بزرگ، می‌تواند تامین‌کننده‌ی خارجی را پیشنهاد دهد — حتی با احتساب هزینه‌های گمرکی و حمل، اگر به‌صرفه‌تر باشد.

### مدلی که iMach نیست

- **بازارگاه بین‌المللی نیست** (مثل Alibaba) — ۹۹٪ کاربران با هم‌وطنان خودشان تجارت می‌کنند
- **پلتفرم صادرات/واردات نیست** — ولی برای خریداران بزرگ می‌تواند پیشنهاد بین‌المللی بدهد
- **فروشگاه آنلاین نیست** — کاربران در iMach خرید نمی‌کنند، فقط ارتباط برقرار می‌کنند
- **سامانه ERP نیست** — ولی می‌تواند با ERP یکپاره شود

## چشم‌انداز

مثل اینستاگرام که هر کاربر ۹۹.۹۹٪ محتوای هم‌زبان خودش را می‌بیند، ولی زیرساخت جهانی است، iMach هم:
- کاربر ایرانی کاتالوگ فارسی می‌بیند، با فروشندگان ایرانی ارتباط می‌گیرد
- کاربر سوری کاتالوگ عربی می‌بیند، با فروشندگان سوری ارتباط می‌گیرد
- ولی وقتی یک خریدار بزرگ ۲۰۰۰ تن مواد اولیه می‌خواهد، iMach می‌تواند تامین‌کننده‌ی خارجی را هم پیشنهاد دهد

**زیرساخت چندزبانه و ترجمه‌پذیر از روز اول مهم است** — نه به‌خاطر صادرات، بلکه به‌خاطر مقیاس‌پذیری بین‌المللی.

## معماری داده

سه لایه‌ی اصلی:

```
Good (نوع کالا) → Product (محصول/SKU) → Listing (آگهی)
```

### Good — نوع کالا (کلاس محصول)

مثل «برنج هاشمی»، «پفک»، «میلگرد آجدار»، «سیب». این یک **کلاس** است، نه یک SKU مشخص.

- هر Good در یک `Category` (دسته‌بندی) قرار دارد
- Good می‌تواند بدون Product باشد (کالای فله/بدون برند)
- `searchText` برای جستجوی سریع نرمال‌شده است (fa-agnostic)
- `nameFa` و `nameEn` — هر Good باید چندزبانه باشد

### Product — محصول (SKU با هویت)

مثل «برنج هاشمی ۱۰کیلویی هیمالیا»، «پفک هوشنگ ۲۰تایی». یک SKU مشخص با برند یا هویت قابل شناسایی.

- `searchText` = **هویت ماشین** (از brand + sorted attr values) — برای find-or-create یکتا
- `label` = **نام نمایشی** — کاربر می‌تواند دلخواه وارد کند (مثل Amazon)
- `barcode` = GTIN/EAN-13 اختیاری — اگر باشد، جستجوی دقیق با ایندکس
- `imageUrl` = عکس مرجع محصول (توسط اولین کاربری که عکس آپلود می‌کند تنظیم می‌شود)

**قانون کلیدی:** فقط کالاهای با برند (یا هویت قابل شناسایی) Product می‌شوند. کالاهای فله (مثل سیب، برنج بدون برند) مستقیم روی Good می‌نشینند — `productId = null`.

### Listing — آگهی

پیشنهاد یک کسب‌وکار برای فروش یا خرید یک Good/Product.

- `mode`: SELL | BUY | BOTH
- `priceMinor`, `stock`, `minOrder` (برای فروش)
- `volume`, `frequency` (برای خرید)
- `gallery`: عکس‌های آگهی (مستقل از Product.imageUrl)
- `variantKey`: کلید هویت آگهی — اگر Product داشته باشد، از searchText محصول می‌آید

## دسته‌بندی (Category)

### ساختار

درخت دو سطحی: **مادر → فرعی**. مثلاً:
```
مواد غذایی و آشامیدنی
  ├── برنج [۱۳ کالا]
  ├── حبوبات [۸ کالا]
  ├── لبنیات [۱۰ کالا]
  └── ...
```

### فیلدها

| فیلد | نوع | توضیح |
|------|-----|-------|
| `slug` | String | شناسه‌ی پایدار، language-agnostic: `dried-fruit` |
| `nameFa` | String | نام فارسی: «خشکبار و آجیل» |
| `nameEn` | String | نام انگلیسی: «Dried Fruit & Nuts» |
| `nameAr` | String? | نام عربی (آینده) |
| `gs1GpcCode` | String? | کد GS1 GPC Brick — برای تطابق بارکد جهانی |
| `hsCode` | String? | کد HS (Harmonized System) — برای گمرک و صادرات |
| `attrs` | Json? | ویژگی‌های پیش‌فرض دسته (weight, packaging, variety, ...) |
| `unit` | String? | واحد عمده‌ی پیش‌فرض: KILOGRAM, TON, CARTON, ... |

### چرا GS1 GPC؟

GS1 GPC (Global Product Classification) استاندارد جهانی دسته‌بندی محصولات است. وقتی یک بارکد EAN-13 اسکن می‌شود، GPC کد آن مشخص می‌کند که این محصول در کدام Brick جهانی قرار دارد.

iMach از GPC برای:
- **تطابق بین‌المللی** — کالای ایرانی و سوری با همان GPC قابل مقایسه
- **استخراج خودکار دسته** — وقتی بارکد اسکن می‌شود، GPC از آن استخراج می‌شود
- **آینده‌ی صادرات** — وقتی خریدار خارجی جستجو می‌کند، GPC مشترک پل ارتباطی است

### چرا HS Code؟

HS Code (Harmonized System) برای محاسبه‌ی هزینه‌های گمرکی. وقتی iMach پیشنهاد می‌دهد که «از سوریه بخر بهتر است»، باید هزینه‌ی گمرک را بداند — که از HS Code محاسبه می‌شود.

### درخت دسته‌بندی فعلی

**۲۴ ریشه، ۹۳ دسته‌ی فرعی، ۵۵۳ کالا.** شامل:
- مواد غذایی و آشامیدنی (۱۷ زیردسته)
- پلیمر، شیمیایی و رنگ
- آهن‌آلات و فلزات
- ابزار و یراق‌آلات
- مصالح ساختمانی
- ماشین‌آلات صنعتی
- کشاورزی و نهاده‌ها
- پوشاک و منسوجات
- کالای دیجیتال
- دام، طیور و آبزیان
- تجهیزات پزشکی
- ضایعات و بازیافت
- و...

### دسته‌ی «سایر › جدید»

وقتی کاربر کالایی ثبت می‌کند که در هیچ دسته‌ای نیست، در `سایر › جدید` می‌نشیند. ادمین باید این‌ها را به دسته‌ی درست منتقل کند. این مکانیزم رشد ارگانیک کاتالوگ را تضمین می‌کند.

## سه قانون توسعه

۱. **کد تمیز + حذف کد مرده** — هرچه اضافه می‌شود، باید تمیز باشد. کد مرده حذف شود.

۲. **سرعت** — همیشه از بهترین راهکارهای کدنویسی استفاده شود تا سرعت لود و انجام عمل‌ها سریع باشد. به‌خصوص لود لیست‌ها.

۳. **سادگی برای کاربر غیرحرفه‌ای** — کاربران iMach عمده‌فروشان و خریداران عمده هستند، نه برنامه‌نویس. UI باید ساده، مینیمال و بدون پیچیدگی باشد.

## جریان‌های اصلی

### ثبت‌نام سریع
کاربر فقط موبایل را وارد می‌کند → User + Business (placeholder) ساخته می‌شود → فرم خوش‌آمد (نام + نوع فعالیت) → ایجاد کاتالوگ.

### ثبت کالا — ۵ روش
۱. **دستی** — انتخاب نوع کالا → انتخاب/ساختن محصول → قیمت‌گذاری
۲. **اکسل** — آپلود فایل → پیش‌نمایش گرید → تأیید گروهی
۳. **از مرجع** — جستجو در Product‌های موجود → تیک‌زدن → قیمت‌گذاری
۴. **با کپی** — جستجوی کاتالوگ همکاران → تیک‌زدن → کپی به گرید
۵. **با اسکنر** — اسکن بارکد → پیدا کردن محصول → اضافه به گرید

### منطق برند → Product
- کاربر صریحاً می‌گوید کالایش برند دارد یا نه (دو رادیو باتن)
- اگر برند دارد → Product ساخته می‌شود (find-or-create با searchText)
- اگر برند ندارد → Listing مستقیم روی Good می‌نشیند (productId=null)
- موتور تطابق از searchText (هویت ماشین) استفاده می‌کند، نه label (نام نمایشی)

### عنوان محصول (label)
- `label` = نام نمایشی — کاربر می‌تواند دلخواه وارد کند
- اگر خالی باشد، بک‌اند از `goodName + brand + attrs` می‌سازد
- `searchText` = هویت ماشین — همیشه از `brand + sorted attr values` — هرگز از label

### عکس محصول
- `Product.imageUrl` = عکس مرجع — اولین کاربری که عکس آپلود می‌کند، آن را تنظیم می‌کند
- `Listing.gallery` = عکس‌های آگهی — مستقل از Product
- کاتالوگ: اول gallery، اگر خالی بود Product.imageUrl

## ذخیره، گوش به زنگ و پرومو

سه مفهوم جدید روی موتور Follow موجود — همه با یک قید آهنین: **هیچ پیچیدگی‌ای که کاربر احساس کند اضافه نشده است.** هر قابلیت فقط در لحظه و جای درستش ظاهر می‌شود؛ کلیک اضافه، فیلد اضافه و توضیح اضافه ممنوع.

### ۱. ذخیره = دنبال کردن قیمت کاتالوگ

واژه‌ی «دنبال‌کننده / فالوور کاتالوگ» برای همیشه کنار است. خریدار کاتالوگ را **ذخیره** می‌کند («ذخیره کاتالوگ») و طرف مقابل **ذخیره‌کننده‌ی کاتالوگ** است. ذخیره کاری ابزاری است (مثل بوکمارک)، نه رابطه‌ی اجتماعی؛ به همین دلیل شمارش آن عمومی و بی‌خطر است.

- هدر کاتالوگ عمومی `/sell/{slug}` تعداد را نشان می‌دهد: «۳۸ ذخیره‌کننده‌ی کاتالوگ» — برای مالک قابل کلیک و بازشدن به فهرست ذخیره‌کنندگان.
- آمار داشبورد فروش و کارت‌ها همه با واژه‌ی «ذخیره» می‌گویند: «ذخیره‌کننده»، «کاتالوگ‌های ذخیره‌شده»، «تابلوهای ذخیره‌شده».

### ۲. تحلیل ذخیره‌کنندگان (سمت فروش)

فروشنده در «مشتریان من» می‌بیند: چه کسی، از کجا و به کدام کالاها گوش است.

- **منبع ذخیره** (`Follow.source`): `ORGANIC` (خودش در اپ پیدا کرد) | `SHARED` (از لینک اشتراکی/کاتالوگ) | `PROMO` (از نمایش پرومو). روی هر ردیف برچسب منبع دیده می‌شود («با لینک» / «پرومو»).
- **تحلیل کالا × ذخیره‌کننده** (`market/getSaverAnalysis`): برای هر کالای فروشی من، ذخیره‌کنندگانی که همان کالا را در لیست خریدشان دارند یا روی آن استعلام زده‌اند — یعنی «قیمت این کالای من را دنبال می‌کنند». مشتق‌شده از داده‌ی موجود؛ هیچ اکشن جدیدی به خریدار تحمیل نمی‌شود.

### ۳. گوش به زنگ (درخواست‌های خریدار)

**«گوش به زنگ» فقط یک اصطلاح فارسی است به معنای «آماده و هوشیار بودن» — هیچ تماس تلفنی/زنگ‌زدنی در کار نیست.** مکانیسمش شبیه فالو است:

- تامین‌کننده از لیست خرید عمومی `/buy/{slug}` یا بازار روی «گوش به زنگ» می‌زند (همان `followBuyer`: صفحه‌ی SELL من → صفحه‌ی BUY خریدار).
- به محض اینکه آن خریدار **نیاز جدید** ثبت کند، درخواستش در **بخش درخواست‌های قیمتِ** فروشنده هم می‌نشیند (`market/getWatchedBuyerNeeds`) و فروشنده می‌تواند همان‌جا پیشنهاد قیمت بدهد.
- خریدار با اشتراک‌گذاری لیست خرید خود، تامین‌کننده‌ها را وارد شبکه می‌کند (اصل چهارم: درخواست خرید خودش دعوت‌نامه است) و گیرنده با یک «گوش به زنگ» ذخیره‌اش می‌کند.
- پیشنهاد به خریدارِ گوش‌به‌زنگ از گیت ۱۰ معرف عبور می‌کند (سرور خودش یال فالو را چک می‌کند) — چون نیاز منتشرشده خودش دعوت است. خریدارِ ناشناس در بازار همچنان پشت گیت است.

### ۴. پرومو — پرداخت به ازای نتیجه (تومان مستقیم)

مدل‌های زمان‌محور (کمپین ۷ روزه) و «اعتبار» کنار گذاشته شده‌اند؛ قیمت‌گذاری مستقیم و به تومان، مثل اینستاگرام:

- **هر نمایش هدفمند: ۱٬۰۰۰ تومان** — نمایش فقط به خریدارِ همان کالا که کاتالوگ فروشنده را ذخیره **نکرده** باشد.
- **هر ذخیره‌ی حاصل از پرومو: ۵٬۰۰۰ تومان** — وقتی همان بیننده کاتالوگ را ذخیره کند، ۵٬۰۰۰ تومان دیگر خرج پرومو می‌شود و `Follow.source=PROMO` ثبت می‌شود.
- فروشنده یک بودجه‌ی تومانی تعهد می‌کند؛ هر رویداد از آن کم می‌شود و پرومو با تمام شدن بودجه خودش تمام می‌شود (`Promo.budgetMinor/spentMinor` به ریال، نمایش به تومان).
- **هدف‌گیری**: پرومو در «تابلوهای ذخیره‌شده»ی خریدار (خوراک `getPriceBoard`) به کالاهای لیست خریدش نشان داده می‌شود؛ هر خریدار به ازای هر پرومو فقط یک بار نرخ نمایش می‌خورد (`PromoEvent` یکتا).
- **تحلیل پرومو**: «۱۲ نمایش · ۳ ذخیره · ۲۷٬۰۰۰ تومان» — اعداد شفاف که تشویق به تکرار می‌کنند؛ کارت پرومو وقتی نتیجه داده، خودش پیشنهاد تکرار می‌دهد.

### جریان‌های ذخیره و گوش به زنگ (خلاصه‌ی اکشن‌ها)

| اکشن کاربر | API | نتیجه |
|---|---|---|
| ذخیره کاتالوگ (خریدار) | `market/followSupplier` (+`source`) | عضو «ذخیره‌کنندگان» فروشنده؛ اعلان «کاتالوگ شما ذخیره شد» |
| گوش به زنگ شدن (فروشنده) | `market/followBuyer` (+`source`) | نیازهای جدید خریدار در درخواست‌های قیمت فروشنده |
| ثبت نیاز جدید (خریدار) | `listings/saveListing` (mode=BUY) | اعلان `BUYER_NEED` به فروشنده‌های گوش‌به‌زنگ |
| پیشنهاد روی نیاز گوش‌به‌زنگ | `market/offerBuyRequest` | بدون گیت معرف؛ همان جریان Offer موجود |
| ساخت پرومو (فروشنده) | `promos/create` | تعهد بودجه؛ شروع نمایش هدفمند |
| توقف پرومو | `promos/stop` | نمایش متوقف؛ باقی‌مانده‌ی بودجه مصرف نمی‌شود |

## دیزاین مرجع — طرح ۸ (نهایی)

مسیر طراحی تا اینجا: **۸ طرح کامل** ساخته و مقایسه شد (`imatch-redesign` ۱ تا ۸ + بریف‌های D5/D6). نتیجه:

- **طرح ۸ (`design-reference-8`) = طرح نهایی و مرجع کامل** — تصمیم مالک (اکتبر ۲۰۲۶): طرح ۸ یعنی **«بیزینس‌مدل طرح ۱ در قالب و زیبایی طرح ۲»** — طرح ۲ به‌عنوان طرح پایه انتخاب و **تکمیل** شد، امکانات طرح ۱ (که کد اصلی فعلی `app/` روی آن است) به آن اضافه شد، و ایده‌های v2 (ذخیره‌کنندگان، منبع رسیدن، شیر لیست خرید، گوش به زنگ، گزارش کمپین، مدل تومانی، شارژ، ورود/ثبت‌نام) در آن اجرا شد. **همهٔ کارهای تکمیلی روی همین طرح اجرا می‌شود.**
- **میراث:** زبان بصری و «کاهش بار شناختی، نه قابلیت» از طرح ۲؛ بیزینس‌مدل و عمق فرم‌ها از طرح ۱ (کد اصلی فعلی). طرح ۲ و طرح ۱ خوانده می‌شوند فقط برای فهم میراث؛ مقصد هرگز نیستند.
- **فاز فعلی (قانون مالک، ۲۰۲۶-۱۰-۰۳): فقط پروتوتایپ.** تمام تمرکز روی **کامل‌کردن و رفع نواقص طرح ۸** است تا به پروتوتایپ نهایی و بی‌نقص برسد. **کد اصلی React و بک‌اند فریز است — تا تأیید نهایی پروتوتایپ هیچ تغییری رویشان وارد نمی‌شود.** پس از تأیید، کد اصلی از صفر کاملاً بازنویسی می‌شود تا از نظر ظاهر و عملکرد ۱۰۰٪ مطابق طرح ۸ باشد.
- **قانون نسخه‌بندی (قانون مالک):** طرح ۸ فقط **یک نسخهٔ واحد** دارد؛ همهٔ اصلاحات **درجا** روی همان اعمال می‌شود. ساخت نسخه‌های جدید (v2، v3، …) ممنوع. در نهایت فقط همین طرح به‌عنوان مرجع باقی می‌ماند و بقیهٔ طرح‌ها حذف می‌شوند. پکیج واحد: `design-reference-8/imatch-redesign-8.zip` (هر تغییر، همین فایل به‌روز می‌شود).

### اصل حاکم

سادگی یعنی **کم کردنِ شلوغی، نه کم کردنِ قابلیت**. هیچ قابلیتی حذف نمی‌شود؛ زمان و جای نمایشش مدیریت می‌شود (Progressive Disclosure). هر عنصری که جریان اصلی را شلوغ کند به لایهٔ دوم می‌رود — زیر همان جریان، در لحظهٔ مرتبط.

### معماری UX (زبان طرح ۸ — میراث طرح ۲)

- **آنبوردینگ یک‌سؤالی**: «الان بیشتر برای چی اومدی؟» → خرید دارم / فروش دارم. انتخاب قفل نیست؛ هر وقت بخواهد از pill هدر بین دو دستیار جابه‌جا می‌شود.
- **دو دستیار مستقل با تب‌بار خودش**: خرید = «لیست خرید | تأمین‌کنندگان | پیشنهادها | پروفایل» · فروش = «کاتالوگ من | درخواست‌های قیمت | پروفایل». سوییچر داخل صفحات ممنوع.
- **تابلوی تأمین خارج از ناوبری اصلی** — همیشه از دلِ کالا باز می‌شود.
- **کاتالوگ = ویترین + مدیریت ظریف**: نمای مالک همان نمای مشتری است + نوار آمار ظریف (بازدید/دنبال‌کننده/درخواست) که ویترین را خراب نمی‌کند؛ آمار کامل در لایهٔ ۲ (شیت).
- **«نمایش ویژه» شفاف**: فقط دیده‌شدن می‌خرد؛ رتبهٔ تطبیق همیشه مستقل از پرداخت.

### پنج قانون طلایی UX (میراث بریف‌های D5/D6)

1. **هم‌زمانی** — کاربر برای کارِ خودش می‌آید؛ شبکه بی‌سروصدا از دلِ همان کار ساخته می‌شود.
2. **نور** — تا پیشنهاد واقعی نباشد، باکس خالیِ «فعلاً پیشنهادی نیست» نمایش نمی‌دهیم؛ جایش قدم بعدی کاربر است.
3. **تشنگی** — کیف پول/پرداخت هرگز در صفحهٔ اول یا ناوبری نیست؛ فقط در عمق پروفایل و شیتِ لحظهٔ مصرف.
4. **زبان** — واژهٔ شبکه‌ای (Network/Matching/Lead/Feed) در UI ممنوع؛ کاربر نتیجه را می‌بیند، اسمش را نمی‌شنود. اعداد فارسی، فعل اول.
5. **صداقت** — پیشنهاد جعلی ممنوع؛ حالت خالیِ صادق همیشه بهتر از پیشنهاد ضعیف است.

### ماتریس حالت‌ها

هر صفحه فقط در حالتِ پر طراحی نمی‌شود: **S0** (روز اول، خالی مطلق — قدم بعدی + دعوت)، **S1** (در حال رشد، شبکه خاموش — بدون باکس خالی)، **S2** (شبکه روشن — «برایت پیدا کردیم»)، **S3** (دروازهٔ ارزش/پرداخت در لحظهٔ تشنگی). حالت خالی هرگز «چیزی نیست» نمی‌گوید؛ همیشه «قدم بعدی این است» می‌گوید.

### ثبت کالا — قانون حضور پنج روش

فرم افزودن کالا/محصول یکی است (یک الگو، دو context خرید/فروش). انتخاب کالا از کاتالوگ مرجع مسیر اصلی است؛ **سه مسیر سریع (اسکنر بارکد، از اکسل، از مرجع) همیشه به شکل یک ردیف فشردهٔ «راه‌های سریع‌تر» زیر فیلد اول حاضرند** — نه دکمهٔ بزرگ، نه منوی جدا. اگر جست‌وجو نتیجه نداد، همین ردیف پررنگ می‌شود. حذف این ورودی‌ها خطای طراحی است (اشتباهی که یک‌بار در جریان «افزودن کالای جدید» رخ داد و نباید تکرار شود).

## نکات مهم برای توسعه‌دهندگان هوش مصنوعی

۱. **کامنت‌ها فارسی هستند** — کل کدبیس از کامنت‌های فارسی برای منطق کسب‌وکار استفاده می‌کند. این عمدی است تا توسعه‌دهندگان ایرانی متن را بفهمند.

۲. **واژه‌نامه‌ی محصول (قانون)**: خریدار کاتالوگ را «ذخیره» می‌کند (نه فالو/دنبال کردن)؛ طرف مقابل «ذخیره‌کننده‌ی کاتالوگ» است. تامین‌کننده «گوش به زنگ» خریدار می‌شود (فقط اصطلاح است — نه تماس). پرومو به «تومان» مستقیم قیمت می‌خورد (نه اعتبار). هیچ رشته‌ای با واژه‌های قدیمی اضافه نشود.

۳. **i18n کلیدها در `i18n/messages/`** — fa.ts و en.ts. هر رشته‌ی قابل مشاهده باید از این مسیر بیاید.

۴. **قانون صفحه‌ی توقف** — هیچ خروجی فقط متنی نیست. همه‌ی خروجی‌ها فایل یا کامپوننت هستند.

۵. **اعتبارسنجی سه‌گانه‌ی فرم دستی**: برند (دو رادیو)، عکس (اجباری برای محصول جدید)، قیمت/موجودی/حداقل (همه اجباری).

۶. **کش بک‌اند**: `goods:tree` با TTL ۵ دقیقه. بعد از تغییر داده، cache invalidate شود.

۷. **مهاجرت DB**: اسکریپت‌ها در `/home/z/scripts/` — مستقیماً MongoDB را آپدیت می‌کنند. بعد از deploy بک‌اند، کش خودکار تازه می‌شود.

۸. **دیزاین مرجع قبل از هر UI** — طرح مرجع نهایی `design-reference-8` است. قبل از ساختن یا تغییر هر صفحه‌ای در `app/`، معادلش را در `design-reference-8` ببین و همان زبان را پیاده کن. طرح‌های ۱ و ۲ فقط برای فهم میراث خوانده می‌شوند، نه به‌عنوان مقصد.
